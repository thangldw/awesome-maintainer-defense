# Awesome Maintainer Defense v1.1 Design

**Status:** Approved for continuous implementation on 2026-08-23.

## Objective

Release Maintainer Defense Kit 1.1.0 as a credible secondary flagship: the documented first run must work, the repository must continuously verify its own contracts, the auditor must model current GitHub Actions authority more accurately, maintainers must be able to adopt it without accepting historical noise, and the project must publish reproducible field evidence without overstating independence.

## Product boundary

The default auditor remains dependency-free, offline, read-only, and usable without a GitHub token. It never executes target-repository code. `fix` continues to emit a unified diff without editing the target. Existing human, summary, JSON, and SARIF output remain supported, and the v1 audit-report JSON schema remains valid.

Version 1.1.0 does not add repository scoring, contributor attribution, automatic issue or pull-request closure, a hosted dashboard, organization fleet management, or live GitHub-settings inspection. Those features either weaken the evidence-first contract or require a separately designed online trust boundary.

## Workstream 1: First-run and repository contracts

The source quickstart will build `dist/maintainer-defense-kit.py` and run that exact path. English, Vietnamese, and Japanese entry points will use the same command sequence. A subprocess regression will extract and execute the quickstart contract in a temporary checkout so a documentation-only path mismatch cannot pass tests again.

The repository will restore static GitHub governance assets removed during the 1.0 consolidation: CODEOWNERS, issue forms for pilot participation, false positives, resource proposals, and documentation corrections, a pull-request template, Dependabot configuration, and read-only quality/workflow-security CI. Product sample workflows under `kits/**/.github` remain data and do not execute in this repository.

Validation will fail when required governance assets are absent, when the public pilot URL names a missing form, when a first-run command points to an artifact not produced by the build, or when committed workflows use mutable Action references or undeclared pins.

## Workstream 2: Authority and trust-path analysis

The auditor will maintain one canonical registry of GitHub token permission scopes. All write-capable scopes documented for GitHub Actions are treated as authority, including `artifact-metadata`, `attestations`, `checks`, `code-quality`, `deployments`, `discussions`, `pages`, `security-events`, and `statuses`. `id-token: write` is modeled as credential-minting authority, not repository mutation, but it still participates in privileged trust-path findings.

Permission evaluation remains job-scoped. A checkout or untrusted execution path cannot borrow authority from an unrelated job, and a safe job cannot borrow `persist-credentials: false` from another checkout step. Existing MD-WF-005 and MD-WF-006 identifiers are extended to use the complete scope registry without changing their public meaning.

The auditor will build a deterministic local workflow index containing workflow name, trigger events, jobs, effective permissions, local or remote reusable-workflow calls, secret inheritance, artifact upload/download steps, checkout references, and executable `run` blocks. This is a constrained GitHub-workflow structural scanner, not a general YAML implementation. It must accept quoted scalars and comments already covered by the corpus, fail closed on invalid command configuration, and avoid claiming safety for syntax it cannot model.

Two new rules are introduced:

- `MD-WF-007`: untrusted GitHub event data is interpolated directly into a shell `run` block. The safe pattern is to pass the value through an intermediate environment variable or a reviewed action input.
- `MD-WF-008`: an untrusted upstream workflow can provide an artifact that a privileged `workflow_run` consumer downloads and executes or sources before authority is removed. The finding must name both workflow files and the evidence path.

The cross-workflow graph only emits MD-WF-008 when all required edges are present locally: an upstream untrusted trigger, an artifact producer, a named `workflow_run` consumer, an artifact download, subsequent execution or sourcing of downloaded content, and secrets or write/OIDC authority in the consumer. Ambiguous chains are not upgraded to critical findings.

## Workstream 3: Adoption controls

The auditor adds three compatible filtering inputs:

- `--baseline REPORT.json` loads a prior schema-v1 report.
- `--compare-ref GIT_REF` audits a temporary archive of the specified local Git revision without executing it.
- `--new-only` emits only fingerprints absent from exactly one selected comparison source.

`--new-only` without one comparison source, or with both sources, is a usage error. Temporary archives are created outside the target and always cleaned up. A nonexistent or non-commit Git ref fails with a specific error and does not silently produce an empty baseline.

Repository-specific suppressions live in `.maintainer-defense.json`, with an optional `--config PATH` override. Each suppression requires `rule_id`, `reason`, `owner`, and `expires_on`, plus at least one of `fingerprint` or `path`. Dates use ISO `YYYY-MM-DD`. Expired suppressions no longer hide findings and produce a stderr warning. Unknown rules, empty justifications, invalid dates, duplicate entries, and suppressions that match neither fingerprint nor path fail validation. Suppression affects presentation and policy thresholds only; raw pilot evidence records both original and effective finding sets.

The audit JSON schema stays at version 1. Filtering produces another valid version-1 report whose summary describes the emitted findings. Comparison and suppression statistics are written to stderr for human runs and into the separate evidence-bundle format for pilots.

## Workstream 4: Pilot evidence

`pilot.schema.json` defines a reproducible evidence bundle with:

- pilot ID, disclosure level, run timestamp, and pilot type;
- auditor version, source commit, standalone SHA-256, command, and target commit;
- raw and effective audit reports;
- per-finding labels: `true-positive`, `false-positive`, `not-applicable`, or `unresolved`;
- recommendation safety/practicality, review effort, remediation outcome, reviewer role, consent statement, and limitations.

`scripts/build_pilot_bundle.py` validates inputs and produces deterministic JSON plus a generated Markdown report. It does not invent labels. Missing labels remain `unresolved`. Aggregate precision or recall is not calculated unless every included finding has an independent label and the sample contract explicitly allows aggregation.

The first 1.1 pilot is a pinned dogfood run against Awesome Maintainer Defense itself at a designated release-candidate commit after the repository governance and CI assets are restored. It is published as `internal-owner-directed`, with technical classification performed during the implementation and the explicit limitation that it is neither independent nor representative. The evidence commit that follows the candidate may change only pilot artifacts and release documentation; runtime-source digests must remain unchanged. The existing ten-repository smoke test remains separate historical evidence.

## Workstream 5: Distribution and release

All package, plugin, documentation, and generated-artifact versions advance together to `1.1.0`. The release build produces:

- `maintainer-defense-kit.py` and compatibility alias `maintainer-defense.py`;
- SHA-256 sidecars and `SHA256SUMS.txt`;
- a universal wheel and source distribution;
- the OpenAI skills/plugin ZIP;
- the pilot evidence bundle and Markdown report.

Release verification installs the wheel and standalone artifact into clean temporary environments, runs a safe fixture audit, validates console entry points, compares all checksums, and verifies the Homebrew formula URL and digest. README download instructions use the exact `v1.1.0` release path and include Linux, macOS, and PowerShell checksum verification.

GitHub CI is least-privilege and pins every Action to a reviewed full commit SHA recorded in `pins.json`. Pull-request CI performs no writes. Release publication is tag-gated and must build from the tagged commit. PyPI publication uses Trusted Publishing from a protected `pypi` GitHub environment; no long-lived PyPI token is committed, printed, or added to the workflow. GitHub release assets and the PyPI files must match locally verified digests.

The ChatGPT plugin bundle keeps a read-only capability declaration, updated 1.1.0 metadata, the canonical auditor skill, references, and standalone script. Positive review tests cover first-run audit, JSON/SARIF, `--new-only`, governed suppressions, and patch-only remediation. Directory copy must distinguish tested engineering behavior from the non-independent dogfood pilot.

## Error handling and compatibility

CLI usage and configuration failures return exit code 1 with a concise stderr message. `--fail-on` continues to return exit code 2 only when the selected policy threshold is reached. A valid audit with zero findings returns 0. Output written through `--output` remains atomic.

Existing rule fingerprints remain stable when their evidence location shifts without a semantic change. MD-WF-005 and MD-WF-006 extensions must not alter fingerprints for existing corpus cases. New fields are not added to schema-v1 reports. Existing installer manifests and uninstall safety behavior remain compatible.

## Verification strategy

Every behavior change follows red-green-refactor:

1. Add a minimal corpus or subprocess regression and observe the expected failure.
2. Implement the narrow behavior.
3. Run the focused test, then `make test` and `make validate`.
4. Commit one independently reviewable change.

The final gate runs auditor tests, installer tests, pilot-bundle tests, distribution tests, metadata checks, pin verification, local-link validation, README quickstart smoke tests, package installation smoke tests, and an audit of the repository's own executable workflows. Network-dependent checks report exact transient failures and are rerun before release; they are not represented as offline proof.

## Release acceptance

Release 1.1.0 is complete only when:

1. all local and CI gates pass at the release commit;
2. the dogfood pilot artifacts reference the designated release-candidate source and target commit, and runtime-source digests are unchanged between that candidate and the release tag;
3. GitHub tag and release assets exist and their published digests match;
4. PyPI exposes version 1.1.0 and a clean environment can install and run it;
5. the ChatGPT plugin version is updated and the directory submission/update is completed, or the exact user-only portal action is identified with a verified bundle ready to upload;
6. post-publication quickstarts succeed against the published artifacts.
